### D2 · 代码推送方式 —— **SSH（修订）**
- **日期**：2026-09-30（初版） / 2026-09-30（修订）
- **初版决策**：因 `github.com:443` 不可达，改用 GitHub 连接器推送。
- **修订原因**：实测发现 **SSH 通道完全可用**——
  - `github.com:22` TCP 可达，`ssh -T git@github.com` 认证成功（身份 `wosongshatang`）
  - 本机 `~/.ssh/id_rsa` 已存在且**已绑定到 GitHub 账号**
  - 而连接器走的是 GitHub App（`Resource not accessible by integration`），
    对私有仓库无访问权、无建仓权，且无法自行授予
- **最终决策**：**使用 SSH 走标准 git 流程**，remote 为
  `git@github.com:wosongshatang/ssl_wb_kh.git`。
- **实测结果**：`git push -u origin main` 成功，远端 `refs/heads/main = 0270e82`。
- **网络现状备忘**：

| 通道 | 状态 | 用途 |
|---|---|---|
| `github.com:443` (HTTPS) | ❌ 不可达 | 不能用 `git push` over HTTPS |
| `github.com:22` (SSH) | ✅ 可达 | **主力通道** |
| `ssh.github.com:443` (SSH) | ✅ TCP 可达 | SSH 22 被封时的备用 |
| `api.github.com` | ✅ 可达 | REST API / 元数据查询 |
| `codeload.github.com` | ✅ 可达（慢） | 下载第三方仓库压缩包 |

- **GitHub 连接器定位（修订）**：仅用于**只读查询**（查仓库/分支/文件/搜索）。
  写操作一律走本地 git + SSH。

## 阶段 2 决策

### D10 · 格挡清除时序 —— **自身回合开始时清零**（Q1 定案）
- **日期**：2026-09-30
- **用户定案原话**：「玩家回合开始时清零，壁垒只是将本该清零的值保留一半，如果没有就是保留 0。」
- **决策**：`Creature.on_turn_start()` 第一步执行格挡清零，清零量**可被钩子改写**：
  - 钩子 `AbstractPower.at_block_clear(clearing, owner) -> int`，返回**实际清零的量**；
  - 默认返回 `clearing`（全清）；
  - **壁垒**返回 `clearing - floor(clearing / 2)`（保留一半，向下取整）。
  - 例：clearing = 5 → 保留 2、清 3；clearing = 0 → 保留 0。
- **为什么这样设计**：设计文档 §3.1 原文把改写点写在 `on_turn_end`，但若格挡在自身回合**末**清除，
  敌人回合来打时格挡已经没了，**格挡机制直接失效**。用户口径（回合开始清零 + 保留本该清零值的一半）
  在机制上与 STS 一致，且表述更精确——它明确了「保留的对象是**本该被清掉的那部分**」。
- **影响**：
  - 阶段 1 的实现方向正确；`clear_block()` 保留并升级为**可被钩子改写**。
  - 阶段 4 做壁垒时只需实现 `at_block_clear` 返回一半，**不需要动 `on_turn_end`**。
  - 设计文档 §3.1 与工程书 §3.1 中关于 `on_turn_end` 的表述**以本条为准**。

### D11 · DamageType 分流**集中在 DamagePipeline**
- **日期**：2026-09-30
- **决策**：`NORMAL / THORNS / HP_LOSS / POISON` 的修正环节分流，由 `DamagePipeline` **集中控制**，
  不在各个 Power 钩子里重复判断类型。
- **理由**：分流规则可测试、且只应存在一份。分散到每个钩子里必然漏掉某一个
  （`card-game-numerical-framework` 技能明确警告过这个陷阱）。
- **代价**：钩子无法自行决定「我要不要参与 THORNS 的修正」。
  将来若确有需要，再给 `AbstractPower` 加 `damage_types: Array[int]` 白名单字段。

### D12 · 钩子集扩展为 10 个（设计文档 §3.3 的 6 个视为下限）
- **日期**：2026-09-30
- **决策**：在 `on_turn_start / on_turn_end / at_damage_give / at_damage_receive / on_card_played / on_kill`
  之外，增加 `at_damage_final`、`modify_block`、`at_block_clear`、`prevent_hp_loss`。
- **理由**：设计文档 §10.3 的修正链本身就含 `at_damage_final_*` 环节；
  `prevent_hp_loss` 必须放在**格挡吸收之后**——缓冲要挡的是「真正会掉的血」，
  被格挡完全吃掉的攻击不该消耗缓冲层数；`at_block_clear` 是 D10 的落点。
- **原则**：钩子默认返回原值，子类只 override 关心的那个。

### D13 · 基础 Power 的文件组织
- **日期**：2026-09-30
- **决策**：`AbstractPower` 基类放 `scripts/identity/abstract_power.gd`（沿用设计文档 §10.4）；
  基础 Power（力量/敏捷/虚弱/易伤/中毒/荆棘/缓冲）集中在

  阶段 4~6 内容变多后若确实需要，再拆成独立文件。

## 阶段 3 决策

### D14 · GameState 与 RunState 的职责划分（**消除双份状态**）
- **日期**：2026-09-30
- **背景**：阶段 0 时 `GameState` 上有 `character_class` 与 `relics`；阶段 3 引入 `RunState`
  后这两个字段在两处各有一份。
- **决策**：
  - **单局资源**（角色 / 幕 / 节点 / 血量 / 金币 / 牌组 / 遗物）→ **只存在 `RunState`**
  - **身份与侵蚀**（转职路径 / 身份能力 id / 神性 / 人性）→ 留在 `GameState`
  - `GameState` 持有 `run: RunState` 与 `map: MapManager` 两个引用
  - 从 `GameState` 移除 `character_class` 与 `relics`
- **理由**：双份状态必然导致「改了这边、读了那边」的 bug，而且极难定位。
  这条与「身份层不可剥夺由架构保证」是同一个思路——**让错误在结构上不可能发生**，
  而不是靠人记得同步。
- **代价**：阶段 0 的 `test_phase0_skeleton.gd` 需同步修改（已改）。

### D15 · 日志级别原则：`push_error` vs `push_warning`
- **日期**：2026-09-30
- **触发**：`SaveManager` 的测试因为 `push_error` 被判失败（GUT 默认把 `push_error`
  计入 `failure_error_types`）。起初看起来是测试配置问题，实际是**日志级别用错**。
- **决策**：
  - **可恢复 + 野外一定会发生** → `push_warning`
    （存档损坏、旧格式缺字段、可选资源缺失）
  - **不可恢复 / 会静默损害用户** → `push_error`
    （写盘失败、必需资源缺失）
- **理由**：用 error 级记录「玩家没有存档」这种事，会让玩家每次启动都看到红色报错，
  而实际体验只是「没有可继续的进度」。级别错了，测试只是先帮你发现而已。
- **附带**：这也是为什么 GUT 的这条默认配置有价值——它逼你认真想日志级别。

### D16 · 卡牌效果按**字段**驱动，不按类型分支
- **日期**：2026-09-30
- **决策**：`BattleManager.play_card()` 依据 `card.damage` / `card.block` 是否为 0 来结算，
  不再 `match card.type` 决定走哪条分支。
- **理由**：按类型分支写不出「攻防一体」牌。`iron_wave`（铁斩波：5 伤 + 5 格挡）
  在按类型分支的实现里，block 会被整块丢掉。
- **`type` 字段仍然保留**：鏖战者（每张攻击牌 +1 怒涛）、风行者（首张攻击牌复制）
  这类终职需要按类型统计。类型是**标签**，不是**效果分派依据**。

### D17 · 分层门禁忽略注释
- **日期**：2026-09-30
- **背景**：`boot_screen.gd` 的注释里提到「BattleScene」，被门禁误判为依赖。
- **决策**：门禁在匹配前先剥掉注释（`sed -E 's/#.*$//'`）。
- **理由**：注释里提一句类名不是依赖。而**误报会让人干脆关掉这道门禁**——
  那比没有门禁更糟。门禁必须保持「零误报 + 零漏报」，做不到前者就先保前者。
- **代价**：字符串字面量里的 `#` 会被误剥（本项目 ui/ 层没有这种写法）。

## 阶段 4 决策

### D18 · 遗物与 Power 的**职责分离**
- **日期**：2026-09-30
- **决策**：**遗物管触发，Power 管数值。**
  - 推荐模式：遗物负责计数与触发 → `apply_power` 施加临时 Power → 由 Power 做数值修正
  - 直接改数值（`AbstractRelic.at_damage_modify`）只用于「无条件、无状态」的简单效果
  - 遗物**不进 `reset_for_battle()`**（生命周期是整局，不是单场战斗）
- **理由**：遗物的生命周期是**整局**，Power 是**单场战斗**。混在一起会让
  「战斗结束清 Power」顺手把遗物也清掉——而且这类 bug 只在第二场战斗才暴露。
- **来源**：`card-game-numerical-framework` 技能的核心原则。

### D19 · 身份能力的注入时机 —— **每场战斗重新实例化注入**
- **日期**：2026-09-30
- **决策**：`GameState.identity_power_ids` 是身份能力的**源头**；
  战斗开始时由 `BattleScene._inject_identity_and_relics()` 清空后重新实例化注入。
- **为什么这样「不可剥夺」是物理性的**：战斗内任何效果（沉默 / 驱散 / 夺能）
  都走 `Creature.remove_power()`，而它**只搜 `powers` 数组**，碰不到 `identity_powers`；
  而身份能力的源头在 `GameState` 上，战斗内代码根本没有引用。
  **不是靠"记得写判断"，而是靠代码结构上够不着。**
- **副作用（正面）**：跨战斗的注入流程天然幂等，不需要额外的清理逻辑。

### D20 · 遗物结算必须在**同步血量之前**
- **日期**：2026-09-30
- **背景**：燃烧之血在战斗胜利时回复 5 点生命。
- **决策**：`_player.notify_battle_end(won)` 必须排在 `_run.sync_from_creature(_player)` **之前**。
- **理由**：顺序颠倒会导致「回的血没被写进单局状态」——玩家在结算画面看到满血，
  回到地图却少 5 点，而且**不会有任何报错**。这类"看起来对、其实错"的顺序依赖，
  必须在代码里写明注释，否则下一个改这段的人一定会踩。

### D21 · 盾猛需要「对手」上下文 → 放在 Creature 上
- **日期**：2026-09-30
- **背景**：盾猛要「对**当前敌人**造成伤害」，但它只有 `owner_creature`。
- **决策**：`Creature.opponents: Array[Creature]`，由 BattleManager 开战时注入。
- **理由**：让 Power 去引用 BattleManager 会让 **Power 层依赖战斗编排层**，
  那样 Power 就没法脱离 BattleManager 单独测试了。放在 Creature 上，
  测试里 `player.opponents = [enemy]` 一行就能构造场景。

## 阶段 5 决策（界面改造）

### D22 · UI 用**程序化构建**，`.tscn` 只留场景根
- **日期**：2026-09-30
- **背景**：用户要求按参考视频重做界面（顶部 HUD / 卡面 / 立绘 / 拖拽出牌 / 结算）。
- **决策**：`.tscn` 只放一个挂脚本的根节点，控件树在 `_ready()` 里用代码搭。
- **理由**：
  1. 本工作流**无法使用 Godot 编辑器**，手写大型 `.tscn` 极易出错且无法可视化检查；
  2. 这些界面的内容几乎全是**运行时才知道**的（手牌、地图节点、奖励选项），
     `.tscn` 里只会得到一个空容器 + 一模一样的构建代码；
  3. 代码构建让"布局与数据"在同一处，改起来只有一个地方要看。
- **代价**：无法在编辑器里所见即所得地调布局。阶段 8 美术化时再把骨架搬回 `.tscn`。
- **例外**：`game_over.tscn`、`boot/main.tscn` 是静态布局，保持 `.tscn` 更合适。

### D23 · 卡牌交互用 **Godot 内建拖放**
- **日期**：2026-09-30
- **决策**：拖拽出牌用 `_get_drag_data` / `_can_drop_data` / `_drop_data`，
  不用手写"鼠标跟随 + 自己算落点"。
- **理由**：内建那套自动处理「拖到哪个控件上」「放下时谁接收」。
  手写实现要在多层 UI（HUD / 弹层 / 手牌）之间算命中，非常容易算错，
  而且错法是"偶尔拖不上去"——最难复现的一类。

### D24 · 战斗结算面板**一次性返回结果**
- **日期**：2026-09-30
- **决策**：金币 / 卡牌 / 药水的选择在面板内部累积，点「继续」时通过一个
  `finished(result: Dictionary)` 一次性返回。
- **理由**：如果做成"点一下发一个信号"，场景要在多个回调间维护中间状态；
  更要命的是玩家还没点「继续」就已经改动了 `RunState`——
  这时崩溃或退出会留下**半成品存档**（拿了金币但没拿牌）。
  一次性返回让「结算」成为**原子操作**。

### D25 · 冒烟门禁的三个坑（**合起来曾让门禁变成摆设**）
- **日期**：2026-09-30
- **背景**：`map_scene.gd` 编译失败时，冒烟测试照样报「4/4 场景通过」。
- **三个坑**：
  1. **只加载场景不足以发现脚本错误**——不在场景依赖图里的脚本根本不会被编译。
     `--quit` 那步毫无反应。→ 改为**逐个编译 `scripts/` 下所有 `.gd`**。
  2. **`SceneTree._initialize()` 里加进树的节点不会触发 `_ready()`**——
     那时场景树还没进入活动状态，`_ready` 被推迟到第一帧。
     所以"挂进树就验证了 `_ready`"是错的。→ 场景检查移到**第一帧之后**。
  3. **实例化失败后根节点没有脚本，但没人检查**。→ 断言 `get_script() != null`。
- **附带**：还加了「进树后子节点数必须 > 0」的断言——程序化构建的界面
  一旦 `_ready` 没跑，子节点数会是 0，这条能直接抓到。

### D26 · 子类**不得**重复声明父类已有的信号
- **日期**：2026-09-30
- **背景**：给 `OverlayPanel` 加 `signal closed` 后，`ShopPanel` 里原有的
  `signal closed` 变成重复声明，编译器报
  `Could not resolve external class member "closed"`，
  **而且错误指向的是使用方（`map_scene.gd`），完全指不到真正的问题点**。
- **决策**：子类不重复声明父类信号；需要时直接用继承来的。
- **教训**：这类错误的"报错位置与真实原因相距甚远"，
  所以**必须有能全量编译脚本的门禁**（见 D25）才能第一时间发现。

## 阶段 5 决策（药水系统）

### D27 · `battle_only` 必须**独立于** `targeting`
- **日期**：2026-10-01
- **背景**：药水分「战斗式」（对敌人）与「通用式」（对自己）。
  但**抽牌药水是自目标却只能战斗中使用**——地图上抽牌毫无意义。
- **决策**：`targeting`（ENEMY / SELF）与 `battle_only`（bool）**两个独立字段**。
- **理由**：靠 targeting 推导不出 battle_only，硬凑会让"自目标 = 通用式"这条
  错误假设蔓延到所有新增药水上。
- **默认值**：`targeting = ENEMY`、`battle_only = true` —— 即用户要求的
  「默认战斗式，除非特别说明」。

### D28 · 药水效果结算收在 `PotionResolver`，**不写进场景**
- **日期**：2026-10-01
- **背景**：药水要在**两个场景**（地图 / 战斗）里用。
- **决策**：效果逻辑全部在 `PotionResolver`；
  `can_use()`（返回**不能用原因**）与 `apply()` 严格分开。
- **理由**：效果逻辑写进任何一个场景，另一个就得复制一份——
  而"复制的那份忘了同步"是最常见的一类玩法 bug。
  地图上用一个**临时 Creature 代理**承接效果，而不是写一套"地图简化版"。
- **`can_use` 与 `apply` 分开的收益**：UI 能明确告诉玩家"为什么用不了"，
  而不是按钮点了没反应。玩家最讨厌的不是不能做，是不知道能不能做。

### D29 · 药水失败时**不消耗**
- **日期**：2026-10-01
- **决策**：`apply()` 返回 `success` 为 false 时**不扣药水**。
- **理由**：药水是一次性资源，「用了没效果还把药水吃掉」是最不能忍的一类 bug。
  所以顺序必须是**先结算、成功了再扣**，而不是先扣再试。

### D30 · 临时牌「战斗结束后消失」**不需要清理代码**
- **日期**：2026-10-01
- **决策**：药水给的牌只进 `DeckManager.hand`，**不进 `RunState.deck_card_ids`**。
- **理由**：每场战斗的牌组都由 `build_deck()` 从 `deck_card_ids` 重建，
  临时牌自然消失。用一个**数据流向**代替一段清理逻辑——
  清理逻辑会漏（忘记在某个退出路径上清理），数据流向不会。

### D31 · 不要给会被外部定位的控件设全屏锚点
- **日期**：2026-10-01
- **背景**：`MapView._ready()` 里设了 `PRESET_FULL_RECT`，
  而场景的 `_layout()` 又设 `position`/`size`。Godot 报
  `Nodes with non-equal opposite anchors will have their size overridden after _ready()`。
- **决策**：会被外部布局的控件，**只由调用方设 position/size**，自己不设锚点。
- **理由**：锚点是"父容器怎么摆我"，position/size 是"我自己在哪"。
  两套机制同时用，后者会被前者在 `_ready` 之后覆盖——
  症状是"布局代码看起来生效了，实际尺寸被改回去了"。
- **配套**：`_layout()` 这类函数**必须在 `_ready` 里立刻调一次**，
  只连接 `size_changed` 是不够的——那要等窗口尺寸变化才触发。
  这正是「地图空白」这个 bug 的根因。
